## Verdict on the five priorities

- **Submit gating: no HIGH.** Every final submit goes through `_Run._submit` →
  `store.begin_submission`, which refuses a preparation-only application and, for a restricted
  one, any packet but the authorized one. `cmd_submit` requires `IMX_ALLOW_SUBMISSION=1`, `--yes`,
  a valid approval and `authorize_submission`; `runner.submit` additionally requires
  `prepare_only=False` and a live authorization (`submission_authorization`, which now lapses on
  `input.received`). One latent bypass exists outside the CLI (L1).
- **Pinning:** runner and store derive the attempt identically (`ATTEMPT_STARTS` /
  `_ATTEMPT_STARTS`, last `packet.saved` per step, question-stop steps override, final step forced
  to the prepared packet); the approved run refuses to submit unless it filled every pinned step
  itself. The equality checks (`preparation_event_id`, `_authorized_packet` vs latest
  `preparation.ready`, `begin_submission` packet id, per-field fingerprint/options/required in
  `approval_mismatches`) hold. One usability dead end (M4).
- **Grounding:** the writer only sees `writer_facts` built from relevant plus kept story chunks,
  the grounder re-checks every rewrite against the same supplied set, and the humanizer keeps the
  last grounded draft. Two ways a contradicted story passage can still reach the writer (M1, M2).
- **Traces / receipts / stdout / --json:** `project_trace` drops value keys and writer reasons,
  `redact_detail` masks quoted values, emails, URLs and digit runs on the approved path, `events`
  and `status --json` reduce URLs to page addresses. One persisted raw site message survives (M3);
  `approve --json` still prints a draft-token URL (L2).
- **Tests:** gaps listed at the end.

## MEDIUM

**M1 — A story passage and the fact extracted from it are dropped independently.**
`packages/browser/src/interviewmaxxing_browser/ai/routing.py:3027-3047`. `_consistency` drops
story-sourced facts (`fact.source == "story:<chunk>"`) from `relevant` (line 3031) and
`_story_consistency` drops chunks from `story_chunks` (line 3033); neither propagates to the
other. Two separate Jev questions (different comparison sets, the chunk one carries `dates_note`
and the field question) judge the same sentence. Failure: the chunk "I spent almost 2 years as
marketing manager…" is judged contradicted and dropped, but the sentence-fact extracted from that
chunk (same text, source = that chunk id, VERIFIED/USER_STATED in the profile, indexed before
round 2c's `tenure_conflicts` skip) has no competing canonical fact under `competing()` (different
key, no shared group) or scores ≥ 0.95 in the other prompt, so it stays in `writer_facts` and the
writer cites "almost two years". The reverse (fact dropped, chunk kept and listed through
`story_evidence`) is equally possible. The tests only cover the two paths separately or both
dropping at once. Fix: after both checks, `gone_chunks = {c["id"] for c in dropped chunks}`;
remove from `relevant` every fact whose source is in `gone_chunks`, and from `story_chunks` every
chunk whose id is the source of a dropped fact; trace the propagated ids under
`story_evidence_dropped` (`fact_ids`/`story_ids`). Add a test for each direction.

**M2 — The cached strong-review verdict skips the story drop for later fields.**
`packages/browser/src/interviewmaxxing_browser/ai/routing.py:2659-2665`. `_consistency` returns
`self._consistency_reviews[revision]` (keyed by the whole candidate revision) before any
comparison, so `dropped` stays empty. Failure: field A drops story fact `sf_x` (line 2759), the
remaining verdicts leave confidence at 0.9, the strong review passes and is cached for the
revision; field B on the same or a later form in the same runtime selects `sf_x` again, hits the
early return with status SUPPORTED, and `sf_x` goes to the writer as evidence. The cached review
never saw `sf_x`. Fix: skip the early return when `dropped is not None` and any selected fact is
story-sourced; or store the dropped story ids with the cached review and apply them
(`dropped.extend(...)`) before returning. Test: two narrative fields, one runtime, story fact
contradicted on the first.

**M3 — Raw site validation messages are persisted and printed.**
`apps/cli/src/interviewmaxxing_cli/runner.py:1208-1223` (`_note_rejections`) stores
`f.validation_error` verbatim in `validation.rejected`; sites echo the typed value
("'avery@example' is not a valid e-mail", "+1 555… is not a valid phone"). `_form_step` calls it
before `_approved_step`, so on the approved path the same text is stored raw one event before
`redact_detail` masks it into `approval_invalidated.details`.
`apps/cli/src/interviewmaxxing_cli/redaction.py:70-88` hides nothing for this event, so
`events APP` without `--verbose`, `events --json` and any ledger consumer show it. Fix: store
`redact_detail(f.validation_error)` (the rejection epoch needs the fingerprint and a message
shape, not the value), and hide `fields[].message` in `public_metadata` unless verbose. Test: a
rejection message quoting an email/phone never appears in events output.

**M4 — A site that resumes its draft is a prepare→approve→submit loop.**
`apps/cli/src/interviewmaxxing_cli/runner.py:1652-1660` refuses (correctly) when the site opened
at a later page, but does so through `_not_approved` (1670-1678), whose message says "prepare it
again, review it and approve it before submitting". Re-preparing lands on the same kept draft,
the new preparation pins the same earlier steps, approval is given again, the next submit
invalidates it again. `docs/submission.md` now says "submit it in the browser yourself"; the
runtime message and the batch summary do not, and every cycle costs a preparation. Fix: a
distinct stop reason for "the site resumed a kept draft at step N" that names the manual remedy
(and, where the browser supports it, walk back through the earlier steps and compare them
instead of refusing). Test on the `site_resumes=True` branch of
`test_pages_filled_before_a_question_stop_are_pinned_and_checked`.

## LOW

**L1** — `apply`/`resume` on a `prepare_only=False` runner can submit an unrestricted
application. `runner.py:826-838`: the gate `if submission and approved is None` only guards
`submit()`. An application with no `application.preparation_only` event (never run by a
prepare-only runner) goes through `_submit` (1755-1760) and `begin_submission`, which skips the
packet check without a restriction event. Not reachable from the CLI (`create_submission_runner`
is built only by `cmd_submit`, which calls `submit`), but the docstring's "every other application
keeps its stored no-submit restriction" is false for never-restricted ones. Fix: in `_submit`'s
non-prepare branch require `self.approved is not None` (or refuse in `_run` when not
`prepare_only` and not `submission`), with an explicit flag for the synthetic e2e path.

**L2** — `approve --json` prints the draft-token URL. `main.py:496` dumps `SubmissionApproval`
with `form_url` as stored, unlike `status --json` and `events`. Fix:
`public_value(approval.model_dump(mode="json"))`.

**L3** — Default retry skips holds that cannot be answered. `retry.py:204-209` runs a
`needs_input` application only when `holds.answered > 0`; `triage.py:236` counts only field
holds, so USER_ACTION (sign-in, CAPTCHA) and UNSUPPORTED_CONTROL holds never count as answered. A
batch application waiting on a sign-in is skipped as "nothing answered since the stop" until
`--all`, which also re-runs everything else. Fix: treat holds without an answer path as eligible
by default, or a separate skip reason and `--user-actions` flag.

**L4** — Story verdict cache eviction breaks at `max_cache_entries == 1`. `ai/stories.py:275`:
`while len(cache) >= max_cache_entries - 1` evicts on an empty dict; `next(iter(cache))` raises
`StopIteration`, not `AIHold`. Fix: `while cache and len(cache) >= max(max_cache_entries - 1, 0)`,
or reserve two slots explicitly.

**L5** — `_OTHER_DOCUMENT` demotes resume labels that mention samples/references.
`ai/classification.py:270-273, 665-670`: "Resume (PDF; writing samples optional)", "Resume/CV —
references on request", "Resume (see licensing note)" match `samples?`, `references?`,
`licen[cs]es?`; the required upload becomes AMBIGUOUS and the resume is not attached. Fail-safe,
but a regression on common labels with no test. Fix: match the other document only as the label's
head noun or when joined to the resume by "or"/"/"; add negative tests.

**L6** — Shared ledger over-counts unreadable submission lines. `main.py:594` reuses the prepare
batch id as the submission batch id when `--batch-id` is absent, so the submission ledger is the
prepare ledger; `batch.py:1828` reads it with `count_unparsed=True`, so a prepare line cut short
by a crash is reported as an unreadable submission line. Fix: `count_unparsed=False` when the
ledger already holds prepare lines, or count only lines after the first `kind: "submission"` line.

**L7** — `status` still prints prompts, candidates and lookup suggestions. `main.py:803-807`
(`describe(item)`) and the `--json` `pending_inputs` (only URLs are reduced, `main.py:770-774`)
show what `events` now hides without `--verbose`. If the `events` policy is the intended one,
batch scripts that keep `status --json` output leak the same values. Decide and document;
otherwise fine as is.
