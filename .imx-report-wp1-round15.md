## 1. The apply control's script click (OpenCLI)

Live: OpenCLI's click on "Apply"/"Apply now" did nothing. The run failed with "Could not
reach the application form … clicked 'Apply'; then clicked 'Apply now'".

Fix (`runtime.open`, `_follow_apply`, `_dom_click_fallback`, `_click_changed_nothing`;
`opencli.OpenCliDriver.dom_click`):
- **When the page is "unchanged".** After an apply click has waited out the settle timeout:
  - the same document and address;
  - still the posting with the control on it;
  - no new visible dialog;
  - no fetch/XHR to the page's own site since the click (`_REQUESTS_SINCE`, read-only resource
    timing; Chromium records a request once its answer is read, so this only adds to the page
    checks).
- **The script click.** The same control gets one `element.click()` through `dom_click`, the
  one fixed script `_DOM_CLICK`. The script refuses disabled elements, anything in a dialog,
  and anything that submits a form.
- **Where it applies.** Only apply controls and apply script links: never a submit or next
  control. At most once per control.
- **The message** says "clicked 'Apply' (DOM click)".
- **Cost.** The unchanged click is known only after the settle timeout (15 s on the lane).
- **Playwright** has no `dom_click` and is unchanged.

## 3. The note reaches the writer as a cover letter

`semantics.classify` gains a `placeholder` input. A textarea asking for a note to the
recruiter or company is `COVER_LETTER`: "Write a note to <recruiter> at <Company>.", "in the
note below", "stand out as a candidate", name `userNote`. Routing's `_route` then uses purpose
`cover_letter`, as for any cover-letter textarea. The runner test shows the writer called with
exactly that purpose.

**Needed from WP12 (writer), not edited here:** a short target for this kind of field.
- **When:** a `COVER_LETTER` textarea whose wording is a note to the recruiter or company (the
  `_NOTE_TO_EMPLOYER`/`_NOTE_ID` shapes in `semantics.py`), or a small `max_length`.
- **Target:** 120–180 words rather than the 280–380-word letter.
- **Keep:** the rubric's hook, one proof and one company sentence.
- **Drop:** gratitude, the applicant's age and the salutation line. The fixture letter opens
  with "Dear Hiring Manager," today.
- **Signal:** the field's semantic and wording already carry it; routing need not change.

## Interim 2 (DONE15b): the approved submit, Wellfound's accepted reading, the rail

- **`submit_approved()`** (the runner calls it only for an approved submission; `submit()` is
  unchanged).
  - It fires when the structured click on the step's submit leaves the page unchanged for the
    settle timeout:
    - same document and address;
    - same step still shown in its dialog, without errors;
    - the submit still enabled and reading the same;
    - no request to the page's own site.
  - Then the same submit gets one `element.click()` through `dom_click_submit`. That second
    fixed script takes only an enabled submit button.
  - Any change or doubt means no repeat.
- **Accepted reading.** A form submitted from a dialog is accepted when, in the same document:
  - the dialog is gone and no form is shown;
  - this job's apply control reads "Applied" (or "Application sent/submitted"), with none of
    this job's left to click;
  - the page names the job.

  Otherwise UNKNOWN, as before.
- **The "Similar Jobs" guard.** Found in the Wellfound schema prior while doing interim 2.
  - Every button and link carries its nearest heading, in its own dialog or page
    (`DomButton.heading`, `DomLink.heading`).
  - Apply controls under a heading over other listings are neither apply controls nor
    submits: "Similar Jobs", "More jobs at …", "Jobs you may like",
    "Related/Recommended/Other jobs".
  - Without it, a working script click on the rail could open another listing's dialog on this
    job's page. DONE15a got an urgent addendum for preparations made with `a4d7489`.

## Tonight's live facts (the lead sent all 30 by driving OpenCLI; folded in before the final commit)

The lead's facts arrived after DONE15b, with the field map of all 30 dialogs
(`.imx/dynamic-applications/wellfound-run/fields.json`, read-only). They corrected two of my
assumptions.

1. **Accepted.** The dialog stays open and says "SUCCESS! YOUR APPLICATION HAS BEEN SENT."; the
   job page's button reads "✓ Applied". Interim 2 read acceptance only when the dialog closed,
   so every live send would have read UNKNOWN. `_dialog_accepted` now accepts when:
   - the dialog states an affirmative acceptance (`ACCEPTANCE` now includes "… has been
     sent"), or it is gone and this job's control reads as applied;
   - none of this job's apply controls is left;
   - the page names the job.

   It is checked before "the form is shown again". `_submit_changed_nothing` also treats a
   success statement or an applied state as an answer, so no script click follows it.
2. **Fields.** The dialogs ask more than a note: the interest question (about 26 of 30),
   phone/LinkedIn/salary/portfolio inputs, radio groups and an empty-name pronouns checkbox
   group, each wrapped in one `<label>`. Required is marked only by "*". Some help texts limit
   answers to 128 characters.
   - `inspect.js`: a `<label>` wrapping several choices is the group's box, even with empty
     names. It is never an option's label; the option texts come from their own boxes, and
     its text outside the options is the question.
   - `normalize`: a limit stated in the help text becomes `max_length`.
   - `semantics`: "the name of the employee who referred you" is free text, not the referral
     source.
   - A blank optional "If yes, please add …" does not block anything.
3. **Fresh tab.** The Apply DOM click works only in a tab that loaded the job fresh. Each run
   already opens its own tab. A second `open` in the same run now closes the driver's own tab
   first (`OpenCliDriver.fresh_tab`).

Mock `wellfound-modal` now keeps the dialog open with the success text, shows "✓ Applied", uses
the live `data-test=JobApplication-Modal`, and has `?fields=screen` (the live shapes, wording
fictional). Tests read the screening dialog, fill it over the bridge and send it in an approved
submit (answers posted, the blank optional answer included), and cover the fresh tab.

## 6. The job's location

- **Place shapes.** `extract_job_identity` reads `jobLocation` as one place or a list: every
  place once, joined with " / ". It keeps region and country: "Austin, TX, US" (`_place`,
  `_job_location`), and handles a country given as an object or an address given as text.
- **Metro rule.** WP2's metro rule reads "Austin, MN, US" as not Austin, TX (test).
- **Form pages.** A form page whose own identity states no location keeps the posting's, when
  both name the same job id or the form's names none (`_with_posting_location`). This applies
  in `open` and in `_continuing_posting` (after a sign-in or consent page).
- **Precedence.** WP9 round 5 makes the saved listing's location win over the page's; this is
  the fallback for jobs outside the inventory.
