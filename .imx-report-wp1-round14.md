These are the step readback's hard path. Round 13 takes an appeared question in only when

Not proven: the stored failures name only the questions, so which other control changed is
not recorded. The mocks reproduce the shape with a button that submits nothing and appears
with the question:
- `greenhouse-eeo?reveal_extra=1`: "Show definitions";

Fix (`runtime.py`):
- **Loose follow-ups.** The question-level change (appeared questions; right after a
  choice, requiredness or help-text changes) is enough when the page is still the same
  application step. `_same_application` compares:
  - the address, title, meta, structured data, job identity, kind and step;
  - every form's request;
  - every button that submits a form;
  - the next and submit controls, by what they are.
  A button that submits nothing does not count.
- **At the step's readback**, the new questions are `SKIPPED` and named, and the page error
  asks for a fresh inspection. The runner inspects the step again, resolves it (the saved
  `hispanic_latino`, `race_ethnicity` and `linkedin_url` answers answer them) and fills it
  before going on to the final review step.
- **During the fill**, the same loose change stops further writes (the round-11 reveal
  path), and the step goes back to inspection the same way.
- **Still a changed page, failed as before:** a reworded or moved question, a question that
  appears already answered, and changed page context or submitting actions. The C4R tests
  pass unchanged.
- **A choice that takes a question away.** Right after a choice this fill made, a question
  that disappears without having been written is a follow-up change too (Paylocity hides
  the end date once "I currently work here" is checked). The readback names it: "1
  question(s) (End Date) disappeared".

A question no answer settles is then held by the resolution like any unanswered required

## 2. Paylocity: "Address Line 1", "Start Date MM/YYYY", "End Date MM/YYYY"

### Address Line 1 (`app_1e7a6775…`: UNSUPPORTED_CONTROL)

The live input is a text combobox whose `aria-controls` list is mounted only once there
are suggestions. So the menu probe found no list, and round 12's address path (`suggests`)
never applied.

Fix (`normalize.py`): an unprobed text combobox whose text wording is an address is a
`TEXT` answer with `suggests` (typed, Escape, read back; a suggestion is never chosen).
Mock: `paylocity-address?address_list=late`.

Residual: on this application Jev read the address's source as the applicant's own at
confidence 0.91–0.92 (0.98–0.99 on `app_340209e9…`). Whether the gate copies it
there depends on that reading, and on the existing identity-scope clarification when the
probability is under 0.95. That is WP10's threshold, not changed here.

### Start Date and End Date (`app_340209e9…`: NO_ANSWER)

Live holds:
- start: "Semantic decision is ambiguous";
- end: "No verified fact or saved answer answers this question".

Fix:
- `interviewmaxxing_generation.work_history` (new) reads the entry and part from the field
  path or section (`txt-workHistory-startDate-0`, `workHistory.currentlyWorkingHere.0`).
- The value comes from the profile's roles (`CandidateProfile.experience`). Entry 0 is the
  most recent role (a current one first, then by start).
- A date is written only in a format the question states (`MM/YYYY`, `YYYY-MM`, a month
  input).
- Every answer cites the role's verified facts; a role without any is not used.
- For a current role, the box is checked and the end date left blank: a non-blocking
  missing input that routing leaves alone.
- "I currently work here" is `CUSTOM_BOOLEAN`, not an attestation (`semantics.py`).

The live route decisions would still have held these answers:
- Jev reads the entry as the applicant's past (`HISTORICAL_OR_CONTEXTUAL`): 1.0 for the
  dates; 0.84 with 0.14 current, at confidence 0.80, for the box.
- For that scope the profile copy is never allowed.

So `routing._gate` now admits exactly this derivation (`_own_work_history`, traced
`work_history`): the same value and the same role's facts, a sure `COPY_KNOWN` route, and
the applicant's own source, current plus historical at 0.95 or more. Another person's
dates never pass.

Mock `paylocity-work-history`: the end date is disabled and hidden while the box is checked.

## 4. The consent page and the "double-check" attestation

**The "double-check" statement** (`app_774a0200…`, `question_17959025004`,
UNSUPPORTED_CONTROL) is one of those ARIA checkboxes. It is now typed `ATTESTATION`
("double-check … information", "information provided … is accurate"). Only the person's
own answer checks it: an exact saved answer, or the statement-coverage decision over
their saved statements (`certify_information_true`).

**Jobvite's "Data Consent" page** (`app_ba808b7f…`, "Accept the data-processing consent",
held in every run since 2026-09-25 00:59) is still reported as a page the person acts on.
`open`, `inspect` and `wait_for_user` still never touch it. The runner now asks first
whether the person's own statement covers it:
1. `data_consent(residence)` reads the page's question without touching the page: a
   one-field form, the required `CONSENT` checkbox "I accept the <policy>" under the page's
   heading. The policy is:
   - the page's only one; else
   - the one naming the person's country of residence (its name, or "US", "U.S.A.", "UK").
   None, or several (Canada in English and in French), leaves the page to the person.
2. The runner resolves it like any consent on a form: an exact saved answer or input, else
   the routing resolver's statement coverage over the person's saved statements
   (`acknowledge_privacy_notice`).
3. Only a checked answer from the person's own answers (`SAVED_ANSWER`, `USER_INPUT`) lets
   `accept_data_consent` act, once per preparation run (a submission run of an approval
   resolves nothing, so there the page stays the person's). It:
   - chooses the policy;
   - waits for the page's one "I Accept" (a button of the consent form or of no form, else
     a link drawn as one; mock `jobvite-like?accept=link`);
   - keeps evidence of the policy shown (`data-consent`);
   - clicks it and reads the form it leads to (with the posting's identity).
4. The runner records `consent.accepted`: the question, the page URL, the source and the
   ids of the covering answers.

A consent no statement covers stops as before ("Accept the data-processing consent").
Accepting sends the consent to the site; it never submits an application.

Open for the lead:
- Whether Jev finds "I accept the Global … APPLICANT AND CANDIDATE PRIVACY POLICY" (section
  "Data Consent") fully covered by `acknowledge_privacy_notice` ("I have read and understand
  the employer's applicant privacy notice and data processing terms.") is Jev's live
  decision. The wording is the page's own and is not tuned toward the saved statement.
- In a prepare-only run, accepting records the consent at Jobvite, as the brief asks.
