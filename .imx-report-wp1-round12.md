## Paylocity (brief items 1–4)

Mock `paylocity-address` (BWA-PL-212, `tests/browser/MOCK_ATS.md`) has all four shapes:
- the two react-widgets DropdownLists, each with its `<label for>` pointing at the div;
- the two input-selects, whose value element covers the input and takes the pointer;
- the address combobox, with its suggestions and status regions;
- a OneTrust banner that slides in `?cookie_ms` after load over the bottom half of the page.

The step form is `novalidate` and its next control is `#btn-submit`; the review page follows.

1. **react-widgets DropdownList.** It is probed like any div menu (the `li[role=option]`
   list mounts inside the widget), becomes a `SELECT` of the shown option texts, is chosen by
   click and is read back from `.rw-input`. "--" (dashes only) is a placeholder.
   - Label: a div is not labelable, so `inspect.js` reads the visible `label[for=<id>]`
     itself, else `data-for` when that text is shown on the page.
   - Required: when that label ends with an asterisk. It is `aria-hidden` on Paylocity; before
     this, the runner never answered the SMS question and the site refused the step.
   - SMS question: `CONSENT`, with the SMS policy as its help text.
   - "Have you worked with us before?": `CUSTOM_SELECT` (see notes).
2. **Input-select.** `DomControl.input_select` reports what the value element shows. The label
   leaves that out ("Country", not "Country United States"). The field is a `TYPEAHEAD` whose
   `FieldBinding.input_select` routes to `aria.fill_input_select`:
   - A display already equal to the answer is left alone (Country "United States",
     "already shows this value").
   - Otherwise it focuses the input (never a click), types the answer, and clicks the one
     option whose normalized text equals it. It then reads the display back (3 s).
   - No equal option: Escape and `NEEDS_CHOICE` with the listed options as suggestions.
     "Colorad" lists "Colorado" and does not take it.
   - The display is the answer, not structure, for the fill guard.
   - The widget is recognised only for a role-less input without `aria-haspopup`, with the
     value element inside its own box. That is narrower than my first version, which also
     took Rippling's role-less location lookup (three lookup tests caught it).
   - Preventive: the browser-validity read before `advance`/`submit` (`_NATIVE_VALIDITY`) skips
     an input-select that shows a choice, since its required input stays empty after a choice.
     One that shows its placeholder is still reported, under its question ("State").
3. **Address Line 1.** An `ADDRESS` input with `role=combobox` + `aria-autocomplete=list` is a
   `TEXT` field (`FieldBinding.suggests`): typed, Escape, read back. A suggestion is never
   chosen. The mock records a pick in `window.__addressPicked`; the tests assert it stays null.
4. **Cookie banners.** Only a decline is clicked:
   - Wording: "Reject All", "Decline", "Necessary cookies only", "Accept only necessary
     cookies", "I do not accept", "Deny", "Continue without accepting".
   - Where: a button outside the application form, or a control of a visible cookie dialog,
     that neither submits nor navigates.
   - When: at `open`, before `inspect` and `fill`, and mid-fill when a banner slides in (the
     guard then declines it and compares the page again). Each button at most once per document.
   - **Behaviour change:** the old accept fallback is gone. "Accept all", "Allow all", "Agree",
     "I agree", "OK", "Got it" and "I understand" were clicked when no decline was found; now
     nothing is. On OneTrust, "Got it"/"OK" is usually the accept handler relabelled.
   - A banner without a decline stays for the person. If it blocks a checkbox or radio, item C's
     dispatched click still sets it.

## Addendum: four live failures of retry five

Each is reproduced on a fictional page. The new tests fail on the j-workspace browser package
(9 of 10; the tenth is the negative phone case) and pass on this branch:
`tests/browser/test_round12_live_fixes.py`.

**A. Lever, "the upload was still in progress when the wait ended"** (app_2e21ec26…).
- The stored screenshot shows the upload finished: "Success!" and the file chip. The
  "Apply with LinkedIn" helper above it was still "Loading…".
- The resume is the form's only file input, so the upload's busy scan covered the whole form.
  The helper's "Loading…" kept `busy` true until the bound (min(settle 15 s, 20 s); the fill
  took 15.7 s).
- A longer wait alone would not have fixed it.
- Fix (`uploads.py` `UPLOAD_STATE`, `runtime._await_upload`):
  - Busy markers count only in the upload's own field (the largest box around the input with no
    other visible field).
  - A marker that already outlasted a bounded wait in the document (`_stuck`) is skipped.
  - While the uploader shows its own progress, the wait lasts up to 60 s (`_UPLOAD_PROGRESS_S`).
    Otherwise it is at most 20 s and the settle timeout, plus 2 s after progress ends.
  - Only a state still in progress at the bound is the mismatch.
- Tests:
  - `linkedin-autofill?loading_ms=600000` (a helper stuck elsewhere);
  - a helper stuck inside the resume's own field (skipped once it outlasted open's wait);
  - an uploader showing "Uploading resume..." for 4 s under a 2 s settle bound.

**B. BambooHR, "questions, bindings, actions, or employer context changed while filling"**
(891 = app_d40d7841…, 881 = app_c4d1ec36…). Both are BambooHR (`zdfirm.bamboohr.com`), not
Greenhouse. Why round 11 did not apply:
- The inspected fields (the routing trace) already held all four Yes/No questions before any
  write. Nothing was revealed, and `_only_questions_added` needed an added question.
- The failure is at the freshness check before sponsorship, right after the authorization
  radio was written. The end-of-fill screenshot shows sponsorship marked required ("*") and
  nothing new on the page.
- A question's fingerprint excludes requiredness, but the guard signature includes each
  control's `required`. So a question that becomes required after another answer trips the
  guard, and nothing let it through.

The events do not name what changed, so the requiredness toggle is the best explanation, not a
proven cause. Fixes:
- `_only_follow_ups_changed` replaces `_only_questions_added`. After a filled choice, questions
  that appeared or became required or optional go down the re-inspect path. It compares with
  `_guard_signature(..., ignore_required=True)`. The page error reads: "1 question(s) ('Will you
  now…') became required after the answer to 'Are you legally authorized…'; inspect this step and
  resolve it again before continuing".
- A reworded or removed question, a changed action or context, or a change after a text write
  still stop (round 11's test for that still passes).
- **Diagnostics:** that stop, and the final readback's "questions on this step changed while
  filling", now say what changed. They give the question's position and field id with the kind
  of change (wording, help text, placeholder, control, options, required, binding), plus
  "actions" or "employer context". No wording or value is included, so redaction keeps it.
  Example: `changed: #5 customQuestionAnswers.yes_no_2102 (required); #6 … (wording)`. Redaction
  turns 4+ digit runs into "…", hence the positions. If the next live retry still fails there,
  this detail names the cause.
- Mock `bamboohr-required` (BWA-BH-183): four BambooHR-shaped Yes/No radios. Sponsorship is
  optional, with no marker, until authorization is answered; then the page marks it required
  (`Field.required_after`, `REVEAL_JS`).
- Tests:
  - the fill re-inspects and a second fill completes;
  - the runner reaches "Prepared to the final review step" in two resolutions, with no failure,
    all four answers on the page and nothing submitted;
  - a rewording still stops, and the detail names `#5 … (required)` and `#6 … (wording)`.

**C. Embedded Greenhouse (careers.upstart.com), "Location Preference": "could not set
#question_… via its label: Locator.click: Timeout"** (app_dbed1cea…).
- The stored screenshot shows plain native checkboxes with labels, not a visually hidden
  input. A fixed cookie dialog ("This website uses cookies", "Manage cookies" / "I do not
  accept" / "I accept") sits over the middle of the viewport, where Playwright scrolls the
  label.
- The runtime never declined it: "I do not accept" was not decline wording, and no accept
  fallback matched "I accept" either.
- Fixes:
  - The decline wording above.
  - `PlaywrightDriver.set_checked` falls back to a click dispatched to the enabled
    checkbox/radio itself, then reads `checked` back. It does this when the input and label
    clicks fail, or at once when the error says another element "intercepts pointer events".
  - Never a `force` click: that would land on the covering element, possibly "I accept".
- Tests:
  - a long form under the fixed dialog: declined ("decline" is the only click), box checked;
  - a full-viewport panel that is not a banner: nothing on it clicked, box checked.

**D. Phone readback on the same application.**
- Fix: `_reads_as_typed` compares a `PHONE` field by digits (formatting, "+" and a leading
  country code 1 on an 11-digit number ignored). It is used by the readback and by the
  end-of-fill sweep, so a formatted number is not typed again.
  - FILLED detail: "the site formats it as '(303) 555-0142'".
- Tests: formatted → FILLED; a site keeping 7 digits → still VERIFICATION_MISMATCH.
- **Caveat:** the stored end-of-fill screenshot shows the Phone Number field *empty*, with an
  intl-tel-input style flag picker. The stored detail is redacted ("reads back '…'"), so this
  application may have ended empty rather than formatted. If so, the digit comparison will not

  runtime used the plain text path there (the detail is `_verify_text`'s), so the picker was not
  recognised as an `iti` phone widget.
